# Exact quantized speculative decoding: early feasibility findings

These are **diagnostic screening results**, not a validated exact algorithm or a paper benchmark. All ratios below are paired `vanilla total latency / method total latency` on the same prompt; a ratio above 1 means the method finished faster. A latency ratio for an inexact output is not an exact-decoding speedup.

## BNB NF4, RTX 4050, 30 prompts, 64-token budget

Source: [`pilot_rtx4050_bnb_n30/rows.jsonl`](pilot_rtx4050_bnb_n30/rows.jsonl), [`analysis.json`](pilot_rtx4050_bnb_n30/analysis.json), and the [`manifest`](pilot_rtx4050_bnb_n30/manifest.json). The prompts are the first 10 from each of the repository's GSM8K, HumanEval, and CNN/DailyMail evaluation files. These inputs were used in previous ZASSD work; the run is a **single-session diagnostic pilot**.

| Method | Exact whole sequences | Mean paired latency ratio | Interpretation |
|---|---:|---:|---|
| Vanilla | 30/30 | 1.000 | Quantized reference |
| PLD batched verification | 23/30 | 1.078 | Faster, but 7 output trajectories differ |
| PLD sequential verification | 30/30 | 0.981 | Reference-equivalent in this test, slightly slower |
| Existing margin guard, threshold 1.5 | 29/30 | 0.197 | Inexact on `cnndm_006`; very slow |

The guard spent an average **77.8%** of its measured request time in canonical replay. If this measured replay time were subtracted for free while keeping every other observed action fixed, its mean latency ratio would be **0.876** over all 30 prompts, or **0.879** over the 29 where the guard happened to match vanilla. Only 1 of those 29 would exceed vanilla under that optimistic cost subtraction. This is a **conditional cost counterfactual**, not an implementable or certified decoder. It suggests that merely making the current guard's full-prefix replay free would not make that policy broadly competitive on this pilot.

A whole-prompt hindsight oracle chose the fastest *observed exact* method separately for each prompt and reached a mean ratio of **1.083**: batched PLD on 19 prompts, vanilla on 6, sequential PLD on 5, guard on 0. This shows some room for choosing among these methods with perfect knowledge, but does not provide an online selector, a cycle-level oracle, or a proof that the selector could be cheap.

The guard's 29/30 at 64 tokens contrasts with an earlier 30/30 held-out result at 32 tokens. The current run is neither a replication on the same cohort nor evidence that the earlier result was wrong; it does show that a calibrated margin threshold cannot be treated as an exactness guarantee. The mismatching guard prompt is `cnndm_006`.

The matched [`cnndm_006` first-divergence trace](cnndm_006_guard_first_divergence.json) uses the pinned Qwen revision, BNB NF4 with double quantization, SDPA and 64 output tokens. Two vanilla repeats agree. The first differing output is token index **12**: vanilla emits `5899`, guard emits `4545`. The first recorded cache hash difference appears at output start 3, after a previous batched verification. At output start 11, a single-token fallback using the active cache selects pending token `4545`; that pending token is emitted at output start 12. The margin guard triggers **during** the cycle at output start 12 and rebuilds canonical KV, but it does not reselect the already chosen pending token. This trace explains this concrete failure path. It does not prove that every guard mismatch follows the same path.

## BNB NF4, same GPU, three 256-token diagnostic prompts

The [paired rows](pilot_rtx4050_bnb_n3_256/rows.jsonl), [run manifest](pilot_rtx4050_bnb_n3_256/manifest.json) and [analysis](pilot_rtx4050_bnb_n3_256/analysis.json) cover one previously used prompt from each of GSM8K, HumanEval and CNN/DailyMail. **Every method generated 256 tokens on each prompt.** This is a one-session stress pilot, not the frozen held-out cohort or a three-model/two-GPU benchmark.

| Method | Whole sequences matching vanilla | Mean paired latency ratio | Mean peak allocated VRAM |
|---|---:|---:|---:|
| Vanilla | 3/3 | 1.000 | 2211 MB |
| Batched PLD | 1/3 | 1.433 | 2216 MB |
| Sequential PLD | 3/3 | 1.021 | 2216 MB |
| Existing margin guard | 3/3 | 0.061 | 2503 MB |

The batched ratio **cannot be described as an exact-decoding speedup** on its two mismatching prompts. The guard's measured canonical replay used an average 94.1% of its request time. Even its conditional free-replay cost calculation reached only 0.992 mean latency ratio, with one of three prompts above 1. Sequential PLD happened to match on all three and averaged 1.021, but empirical equality on three sequences is not a theorem. These results strengthen the case for a shape-invariant verification path or a genuine state-error certificate before policy tuning.

## Single-prefix linear shape probe

The [`Qwen2.5-0.5B BNB probe`](qwen05b_bnb_linear_shape_probe.json) compared five candidate-token positions after the same 75-token prefix. Ordinary batched verification differed from sequential verification in logits by 0.1875–0.2734 max absolute per row, flipped one of five row argmaxes, and produced nonzero KV differences starting at layer 1. A diagnostic variant forced all 169 quantized linear/LM-head modules to invoke their original kernel separately on each token row (845 one-row calls). Its five argmaxes matched sequential verification, **but logits and KV still differed**, with the first KV difference again at layer 1. Thus quantized linear execution shape can affect a decision in this one prefix, while changing linear calls alone does not establish whole-model shape invariance. The variant is intentionally slow and is not a decoding algorithm or proof.

The same probe on the main [`Qwen2.5-3B target`](qwen3b_bnb_linear_shape_probe.json) used five candidate positions after a 37-token prefix. Both ordinary batched and singleton-linear batched execution matched sequential argmax on all five rows, yet both had nonzero logit and KV differences, again starting at layer 1. This second prefix supports the narrower conclusion that normalizing only the quantized linear calls does **not** restore state equivalence. The operator-hook audit below localizes one early difference.

A third probe on [`Llama-3.2-1B`](llama1b_bnb_linear_shape_probe.json) also found nonzero logit and KV differences beginning at layer 1 after a 75-token prefix. All five argmax decisions happened to match in both batched variants. These are three **single-prefix diagnostics**, not the planned three-model, 256-token validation.

The instrumented module audits on [`Qwen2.5-0.5B`](qwen05b_bnb_operator_shape_audit.json), [`Qwen2.5-3B`](qwen3b_bnb_operator_shape_audit.json) and [`Llama-3.2-1B`](llama1b_bnb_operator_shape_audit.json) all found the same candidate intrinsic shape-sensitive operator: `model.layers.0.self_attn.q_proj`. In each audit, the recorded primary input tensor was bitwise equal between one-token and five-token execution, while the 4-bit projection output differed by a maximum of 0.0625, 0.0625 and 0.03125 respectively. This directly localizes one early source of shape-dependent numerical error under BNB NF4. Hooks record only the primary tensor input and first tensor output; the result does not establish that q_proj is the only source, and it does not supply a global error bound.

### Phi-3.5-Mini BNB shape probe

To add an independent architecture family, [`microsoft/Phi-3.5-mini-instruct`](https://huggingface.co/microsoft/Phi-3.5-mini-instruct) was loaded at pinned revision `2fe192450127e6a83f7441aef6e3ca586c338b77` in BNB NF4, double-quantized FP16 compute and SDPA. On the previously used 481-token `cnndm_002` development prefix, M=3/5/9 each had matching argmaxes at every candidate row, while ordinary batched logits differed from sequential by up to 0.53125/0.578125/0.578125 and active KV differed at all three M values. Splitting 4-bit linears into single-row kernel calls did not restore KV equality.

The [operator-hook audit](phi35_cnndm002_operator_shape_k4_v1.json) found 129/129 hooked modules with differing outputs overall. The first hooked module with bitwise-equal primary input but differing output was Phi's `model.layers.0.self_attn.qkv_proj` (output max difference 0.015625). At M=5 the first differing KV layer moved from layer 0 in ordinary batching to layer 1 with singleton-linear calls. See the [consolidated report](phi35_shape_forensics_cnndm002_v1.json) and raw [M=3](phi35_cnndm002_shape_k2_v1.json), [M=5](phi35_cnndm002_shape_k4_v1.json), and [M=9](phi35_cnndm002_shape_k8_v1.json) probes. This is one prefix and no multi-cycle token divergence was measured; it extends the shape-sensitivity observation beyond Qwen/Llama but does not establish B1 correctness on Phi.

### Cross-model shape-sensitivity sweep

To test whether the numeric effect was confined to one checkpoint, M=5 was measured under the same BNB NF4/FP16/SDPA runtime on two common long development prompts (`cnndm_001` and `cnndm_002`) across seven checkpoints: Qwen2.5 0.5B/1.5B/3B, Llama 3.2 1B/3B, Phi-3.5-Mini 3.8B, and OLMo 2 1B. The [14-configuration aggregate](crossmodel_shape_sweep_m5_two_prompts_v1.json) shows nonzero logit and active-KV differences in **14/14** configurations. Candidate-row argmax agreed in 69/70 positions; the lone mismatch was Qwen2.5-0.5B on `cnndm_001`. After splitting quantized linear calls into singleton rows, candidate argmax agreed in 70/70 positions, but KV still differed in 14/14 configurations.

Instrumented M=5 runs locate the first equal-primary-input/different-output module in the initial Q/K projection family: `q_proj` for Qwen2.5-3B, Llama 3.2-3B and OLMo 2 1B; Phi uses fused `qkv_proj`. See the [Qwen](crossmodel_operator_qwen25_3b_cnndm002_m5_v1.json), [Llama](crossmodel_operator_llama32_3b_cnndm002_m5_v1.json), [OLMo](crossmodel_operator_olmo2_1b_cnndm002_m5_v1.json), and [Phi](phi35_cnndm002_operator_shape_k4_v1.json) audits. This supports a general claim about **shape-sensitive BNB NF4 numerical state changes across these four architecture families in this pinned runtime**. It does not show universal token divergence: only one of 70 candidate-row decisions flipped, two prompts are a narrow sample, and fixed-row B1 remains implemented only for Qwen2. To claim broad model support, the next step is a model-adapter/capability contract that validates the relevant projection, attention, cache, and rollback properties per architecture and fails closed when they are not established.

#### Locked cross-task and M expansion

The [locked protocol](crossmodel_shape_sweep_protocol_v1.json), [frozen 9-prompt cohort](crossmodel_shape_cohort_v1.jsonl), [aggregate run summary](crossmodel_shape_sweep_v1/summary.json), and [stratified analysis](crossmodel_shape_sweep_v1/analysis.json) extend that screening to 7 pinned checkpoints × 3 tasks × 3 proposal lengths (M=3/5/9), for 189 completed configurations with no failures. The cohort uses three development prompts each from GSM8K, HumanEval and CNN/DailyMail; GSM8K test indices 300–349 were excluded. Backend remained BNB NF4, double quantization, FP16 compute and SDPA on one RTX 4050 runtime.

Ordinary batched verification had nonzero logit drift in **189/189** configurations and active-KV drift in **188/189**. Candidate-row argmax matched in **1052/1071 (98.2%)** positions; 18/189 configurations had at least one flipped candidate-row argmax. This is a prefix-local diagnostic and must not be reported as a full output exactness rate. Every task stratum had logit drift in 63/63 configurations; active-KV drift occurred in 62/63 GSM8K and 63/63 for HumanEval and CNN/DailyMail. At M=3/5/9, argmax agreement was 186/189, 309/315 and 557/567 respectively, so there is no evidence here that larger M removes the numerical drift.

|---|---:|---:|---:|---:|
| Qwen2.5-0.5B | 27/27 | 27/27 | 147/153 | 149/153 |
| Qwen2.5-1.5B | 27/27 | 27/27 | 151/153 | 149/153 |
| Qwen2.5-3B | 27/27 | 27/27 | 151/153 | 153/153 |
| Llama-3.2-1B | 27/27 | 26/27 | 153/153 | 153/153 |
| Llama-3.2-3B | 27/27 | 27/27 | 151/153 | 153/153 |
| Phi-3.5-Mini | 27/27 | 27/27 | 150/153 | 150/153 |
| OLMo-2-1B | 27/27 | 27/27 | 149/153 | 151/153 |

The singleton-linear intervention increased aggregate argmax matches from 1052 to 1058, but left logit drift in 188/189 and KV drift in 188/189 configurations. Its effect varied by checkpoint: it repaired the candidate-row flips for Llama-3.2-3B and Qwen2.5-3B, while Qwen2.5-1.5B had two more flips afterward. Thus this intervention is evidence about one possible source of shape sensitivity, not a general correction. The measured signal generalizes across all seven checkpoints, four architecture families, three tasks and three M values in this pinned backend/runtime. It still does not establish universal model/runtime behavior, B1 correctness outside the Qwen2 implementation, multi-cycle token equivalence, or full-sequence exactness.

#### Expanded prompt cohort and independent session repeat

The next locked protocol used 10 prompts per task from the local extended development sources (`gsm8k_ext150`, `humaneval_ext114`, and `cnndm_ext150`), 7 pinned checkpoints, M=3/5/9, and two separate Python processes. Each session completed all **630/630** configurations without failure. The two sessions reproduced the candidate IDs and every ordinary and singleton-linear logit/KV metric exactly in **630/630** matched configurations. The selected IDs were absent from earlier exact-feasibility shape-sweep result files, though some had appeared in general benchmark runs elsewhere in this workspace; this is broader development evidence, not an untouched held-out cohort. The exact prompt/source hashes and run manifests are in the [locked protocol](crossmodel_shape_repeat_protocol_v1.json), [cohort](crossmodel_shape_expanded_cohort_v1.jsonl), and [session directories](crossmodel_shape_repeat_v1/).

Across either session, ordinary verification had logit drift in **626/630** configurations and active-KV drift in **623/630**. Candidate-row argmax agreed in **3539/3570 (99.1%)** positions; 31/630 configurations had at least one flipped candidate-row argmax. Per checkpoint, logit drift was present in 86–90/90 configurations, KV drift in 86–90/90, and candidate-row argmax agreement ranged from 499/510 for Phi-3.5-Mini to 510/510 for OLMo 2 1B. By task, logit drift was 206/210 on GSM8K and 210/210 on each of HumanEval and CNN/DailyMail. The detailed model/task/M splits and session comparison are in [analysis.json](crossmodel_shape_repeat_v1/analysis.json).

One repeatable outlier is Phi-3.5-Mini on `gsm8k_059`, M=9. Both sessions used identical candidate IDs and recorded max logit difference **25.125**, KV key difference **12.875**, and KV value difference **17.46875**. This occurs at candidate row 5 (zero-based), whose candidate token is newline (ID 13); all nine candidate-row argmax decisions nevertheless match. Singleton-linear calls reduce the KV maxima in that configuration to 4.3046875/3.375 but leave a 24.640625 maximum logit difference. It is a reproducible state/logit divergence for this particular continuation, not a token-row flip or a full-generation mismatch measurement. The broad cohort therefore strengthens reproducibility of the finite-precision shape-sensitivity claim while also showing that argmax flips are sparse and that error magnitude can be highly prompt/model/continuation dependent.

The [layerwise trace](phi35_gsm8k059_m9_error_growth_diagnosis_v1.json) localizes the first recorded perturbation to `model.layers.0.self_attn.qkv_proj`: its primary input is bitwise equal, while its output differs by 0.03125. Candidate row 5 then grows to a maximum decoder-layer output difference of 0.5 at layer 12, 2.625 at layer 13, 11.75 at layer 19, and 732.75 at layer 29. The largest late module deltas are in MLP `down_proj` at layers 25 and 29–31. This supports an early shape-dependent perturbation followed by depth-wise amplification in this trajectory; the hooks do not observe every internal attention argument/state and cannot establish a unique causal chain.

## B1 fixed-row prototype

The implementation is in [`src/zassd/certification/qwen2_padded.py`](../../src/zassd/certification/qwen2_padded.py), [`src/zassd/decoding/b1_exact.py`](../../src/zassd/decoding/b1_exact.py), and runner [`scripts/run_b1_block_pilot.py`](../../scripts/run_b1_block_pilot.py). The singleton `b1_exact_generate` uses the original one-token target call and canonical cache. The fixed-row reference pads each decode-time Qwen2 linear/RMSNorm call to a pinned physical row count and computes attention one query at a time against the corresponding causal KV prefix. The block prototype applies that same physical row count to the speculative block, crops cache to the accepted prefix, and keeps draft tokens out of target KV.

The first block probe exposed an important dispatch difference: passing an all-zero causal mask changed SDPA results even when query, key and value shapes matched. The `rowwise` attention path therefore truncates K/V to the logical causal prefix and passes no mask. An alternate `padded` path pads Q/K/V and uses an explicit causal mask so every singleton and block call uses fixed SDPA shapes. On the pinned Qwen2.5-3B NF4 setup, the padded path matched logits and KV bitwise for M=1..9 in the recorded single-prefix probe [`b1_probe_qwen3b_rows9_padded.json`](b1_probe_qwen3b_rows9_padded.json). These probes are finite implementation checks, not a proof for every prompt or runtime.

### Repeated K sweep

The first three development prompts and the next row from each task were measured in two independent repeat rounds. Each prompt compares original BNB greedy, B1 singleton, and B1 block. Method order rotates by prompt and round; K order was K=2/4/8 in round 0 and K=8/4/2 in round 1. The added prompts (`gsm8k_001`, `HumanEval/1`, `cnndm_001`) have appeared in earlier workspace experiments, so this is a wider B1 development measurement, not fresh or held-out data. Full raw rows and manifests are in the run directories under the [`first prompt-window runs`](b1_repeat_s0_k2) and [`second prompt-window runs`](b1_extension_s0_k2_rows1) prefixes. The validated combined aggregate is [`b1_k_sweep_expanded_six_prompts_v2.json`](b1_k_sweep_expanded_six_prompts_v2.json).

| K / rows | Mean BNB speedup, round 0 / round 1 | Pooled mean / geometric mean | Exact B1; exact BNB |
|---|---:|---:|---:|
| 2 / 3 | 1.095× / 1.081× | 1.088× / 1.078× | 12/12; 4/12 |
| 4 / 5 | 0.938× / 0.906× | 0.922× / 0.899× | 12/12; 2/12 |
| 8 / 9 | 0.978× / 0.955× | 0.967× / 0.945× | 12/12; 2/12 |

Across 12 paired prompt-round measurements, K=2 beat K=4 by a mean paired latency ratio of 1.178× and K=8 by 1.159× (other-K latency divided by K=2 latency). K=2 had the best BNB-relative speed in both rounds. The aggregate ratios still vary by task and prompt: K=2's six-prompt means were 0.989× on GSM8K, 1.219× on HumanEval and 1.057× on CNN-DM. Every block run matched its B1 singleton token sequence and every shared cycle-frontier KV digest matched. BNB sequence equality was 4/12 for K=2 and 2/12 for K=4/8. The added prompts had prior use elsewhere in the workspace, results are from one GPU and two rounds, and the sample remains too small for a general or held-out claim.

The separate single-prefix [`M=1..9` probes](b1_fixed_row_qwen05b_m9.json) and [`3B rowwise probe`](b1_fixed_row_qwen3b_m9.json) report bitwise-equal logits and KV for every tested M at one prefix per model. The padded path also passes [`M=1..3`](b1_probe_qwen3b_rows3_padded.json), [`M=1..5`](b1_probe_qwen3b_rows5_padded.json) and [`M=1..9`](b1_probe_qwen3b_rows9_padded.json) on one 3B prefix. The 64-token K=4/rows=5 runs compare 44–63 shared cycle-frontier state hashes per prompt; all shared hashes match. The 256-token runs compare token outputs and KV hashes only at shared cycle frontiers, not at every generated token. All prompts are previously used development inputs, and no held-out result is claimed.

This is a promising B1 prototype, not B2: fixed-row shape and selected attention strategy are part of the new greedy reference. Across six prompts, K=2 remains the strongest BNB-relative candidate among K=2/4/8 with 1.088× pooled mean and 1.078× geometric-mean speedup, but it is slower than BNB on some prompts and differs from BNB's token sequence on 8/12 paired observations. Against fixed-row singleton, mean speedup rises with K (1.469×, 1.557×, 1.622× for K=2/4/8). All configurations matched B1 outputs in all 12 prompt-round runs. The padded path removes the Python rowwise SDPA loop, but still uses padded BNB linear calls. On 0.5B, earlier rowwise runs were faster in three prompts but differed from original BNB on one prompt for K=2/4/8.

The implementation-specific [Qwen2 fixed-row operator contract](QWEN2_FIXED_ROW_OPERATOR_CONTRACT.md) is now written. The context manager rejects non-Qwen2 models, external masks/positions, and unsupported decode cache/modes; a guarded M=1..3 probe still matches bitwise. Padded token IDs still cannot be inferred reliably. The runner now records a packed model/quantization-state digest, and the branch audit exercises rejects, pending-token EOS, one accepted EOS draft, and budget completion. Broader cache-boundary coverage remains open. The conditional margin helper in `src/zassd/certification/greedy.py` still has no validated backend bounds.

### Per-cycle oracle pilot

The [K=1/2 cycle oracle](b1_cycle_oracle_k1_k2_v5.json) uses three previously seen development prompts, two process sessions, 64 output tokens and the fixed rows=3 reference. It includes measured draft/verify/commit wall times and keeps only actions whose token sequence and audited cache frontier match B1. Complete paths were found for 3/3 prompts. The median predicted speedup over B1 singleton was 1.211×; median gain over the best fixed-K path under the same additive cycle-cost model was only 1.0005×. This suggests no useful K-switching gain in this small sample. The oracle has future knowledge and omits selector, switch, checkpoint and broader cache-copy costs; treat it as an optimistic diagnostic, not an online policy or performance claim. Median cycle component-sum error was about 18 microseconds per cycle. As in the long-context pilot, cycle timing excludes trace-list append/state-observer hashing and the non-cycle residual is calibrated from observed runs; it may vary with cycle count.

The [independent repeat audit](b1_reference_repeat_audit_v3.json) also records 3/3 prompt token sequences and prefix KV digests equal across sessions for K=1/2. The GSM8K 300–349 cohort remains unused.

### Long-context, 256-token cycle and cache-cost audit

The [long-context cycle oracle](b1_cycle_oracle_long_cnndm_v2.json) uses the previously seen `cnndm_000` prompt (397 input tokens), 256 output tokens, fixed rows=3, and K=1/2 across two process sessions each. B1 block matched the singleton on 4/4 runs; original BNB matched 0/4. Singleton token and active-KV digests were identical across all four runs, with all shared block frontiers equal. The oracle path completed and used 184 cycle actions (91 K=1, 92 K=2, plus an already-pending terminal token); it predicted 1.456× versus singleton and only 1.0217× over fixed K=2 under the additive cycle model. Cycle intervals omit trace-list append and state-observer hashing; the per-request residual is calibrated from observed runs and may shift with a different cycle count. It switched K 64 times and saved about 133 ms in its idealized estimate, so the break-even unmodeled switch cost is about 2.07 ms each. This remains a one-prompt hindsight ceiling without selector/checkpoint costs.

The [per-schedule summary](b1_long_context_k_schedule_summary_v1.json) extends this same long-context prompt to K=4/rows=5 and K=8/rows=9, each with a separate singleton contract. Across two sessions per schedule, B1 block matched its own reference and shared KV state 2/2 for K=1,2,4,8; original BNB matched 0/2 in each group. Median block-over-singleton speed ratios were 1.294×, 1.456×, 1.733× and 1.832× respectively. These are within-contract measurements; physical row count changes the singleton reference, so they are not one common token-trajectory comparison. K4 and K8 per-cycle traces have complete paths under their own contracts and show no adaptive gain over their corresponding fixed K.

Contract-bound [operator probes](b1_operator_probe_long_cnndm_rows3_v1.json), [rows=5](b1_operator_probe_long_cnndm_rows5_v1.json) and [rows=9](b1_operator_probe_long_cnndm_rows9_v1.json) use the same 397-token prompt. They found bitwise-equal logits and active KV for M=1..3, M=1..5 and M=1..9 respectively. At M=2, the instrumented module outputs and attention tensors also showed no differences. These are finite same-prefix probes; the hook captures only selected module inputs/outputs and do not establish the operator contract universally.

The [cache primitive benchmark](b1_cache_checkpoint_cost_cnndm_v1.json) measured a 24.0 MB active KV prefix at length 652. Median host-wall times were about 0.011 ms for zero-copy fork, 0.005 ms for logical crop/length restore, 0.441 ms to restore an existing checkpoint, and 0.897 ms for clone plus restore. A hypothetical full clone/restore at each of the oracle's 64 K switches would cost about 57 ms, consuming part of the 133 ms idealized margin. This is a diagnostic cost model: the implementation does not yet use this checkpoint design, and the measured primitive may not represent an optimized checkpoint path.

On `cnndm_002`, K=2/rows=3, K=4/rows=5 and K=8/rows=9 each matched the B1 singleton at all 256 recorded prefix states (output prefixes 0–255), including the final canonical cache before the pending budget token. This closes the sampling gap for active KV on this finite prompt/runtime; the digest does not include unused static-cache suffix bytes or every hidden backend state, and one session per K is not a universal proof.

#### Llama-3.2-1B fixed-row adapter

The Llama-specific fixed-row schedule and architecture dispatcher are implemented in [`llama_padded.py`](../../src/zassd/certification/llama_padded.py) and [`fixed_row_dispatch.py`](../../src/zassd/certification/fixed_row_dispatch.py). For the pinned `unsloth/Llama-3.2-1B-Instruct` revision `5a8abab4a5d6f164389b1079fb721cfab8d7126c`, BNB NF4/FP16 compute and SDPA, the sequential-versus-batched probes matched logits, candidate argmax, and active KV prefixes bitwise for every M=1…9 on GSM8K, CNN/DailyMail and HumanEval. Both padded and rowwise attention strategies passed these shape probes.

The B1 pilots compared fixed-row block decoding to fixed-row singleton decoding over 64 output tokens on one prompt from each task. Every token and committed KV prefix matched for all 192 prefixes per attention strategy. Each run had 152 block cycles, 140 draft tokens and 40 accepted draft tokens; 29 cycles rejected a draft at positions 0, 1 or 3. Artifacts are in [`llama32_1b_b1_adapter_pilot_v1`](llama32_1b_b1_adapter_pilot_v1/) and [`llama32_1b_b1_adapter_pilot_rowwise_v1`](llama32_1b_b1_adapter_pilot_rowwise_v1/), with shape probes named `llama32_1b_fixed_row_*_rows9_v1.json`. This is a narrow, same-runtime development pilot: it does not establish performance gains, held-out accuracy, other Llama checkpoints, other backends, or formal all-input exactness.

The pinned Llama-3.2-3B revision `006f5dcd1393c3add266de40994ba96225e9689d` also passed all six M=1…9 probes (three tasks × two attention strategies) and both 64-token B1 pilots: 3/3 token matches and 192/192 KV-prefix matches per strategy. Its artifacts are `llama32_3b_fixed_row_*_rows9_v1.json` and [`llama32_3b_b1_adapter_pilot_v1`](llama32_3b_b1_adapter_pilot_v1/), [`llama32_3b_b1_adapter_pilot_rowwise_v1`](llama32_3b_b1_adapter_pilot_rowwise_v1/). This adds a second model size in the Llama family, within the same pinned runtime and development cohort.

The [paired performance pilot](llama32_3b_perf_rowwise_session0_v1/summary.json) adds two process sessions for each attention strategy on the same three prompts (12 paired rows total). Every block matched the fixed-row singleton (12/12), while only 8/12 matched original BNB greedy; both CNN/DailyMail runs per strategy differed from original BNB. Mean block speedup was **1.279× vs fixed-row singleton** (median 1.305×), but only **0.603× vs original BNB greedy**. The strategy means vs BNB were 0.590× rowwise and 0.616× padded. Thus the prototype's block path does not yet deliver an end-to-end speedup over the ordinary quantized baseline; fixed-row operator overhead dominates on this sample. These are short development measurements on one GPU and are not a performance claim.

A K/physical-row sweep compared padded K=1/rows=2, K=2/rows=3, K=3/rows=4 and K=4/rows=5 (two sessions × three prompts each). All 24 block outputs matched fixed-row singleton; 16/24 matched original BNB, with CNN/DailyMail mismatching in every BF16 run. Mean speed ratios against original BNB were **0.911× (K=1)**, **0.918× (K=2)**, **0.605× (K=3)** and **0.616× (K=4)**. K=2 was the best BF16 setting tested but remained slower than original BNB. A separate FP16 model-dtype K=2/rows=3 experiment matched original BNB on 6/6 rows, but its mean speed ratio was only **0.881×**. It improved absolute B1 block time in this sample but also sped up the vanilla baseline more; it is not enabled by default. Full aggregates are in [`llama32_3b_b1_tuning_summary_v1.json`](llama32_3b_b1_tuning_summary_v1.json). The session artifacts are under `llama32_3b_perf_padded_k*rows*_session*_v1/` and `llama32_3b_perf_fp16_k2rows3_padded_session*_v1/`.

The [operator profile](llama32_3b_ops_profile_padded_v1/analysis.json) shows that BNB 4-bit GEMM kernels accounted for **75.9%** of aggregate CUDA kernel duration (76.2% rowwise); Flash attention was under 1%. With K=4/rows=5, the 20-cycle trace recorded 3,360 BNB GEMMs with input `[1,5,3072]` and 560 with `[1,5,8192]`. The `[1,5,*]` shapes are the cost of padding every projected decode row to the fixed physical row count. Attention strategy changes the Flash-attention launch count substantially, but not the dominant 4-bit GEMM count. The current optimization target is therefore the quantized linear path and its fixed-row execution, not attention masking.

An opt-in Llama experiment reuses a per-linear output buffer for zero padding via `constant_pad_nd.out`, instead of allocating a new `F.pad` result on each call. The [within-process paired A/B](llama32_3b_reusable_pad_paired_ab_v1/summary.json) ran 12 pairs on the three prompts. Both variants matched singleton tokens and all KV prefixes in every run. Reuse-buffer speed was **0.967×** the fresh `F.pad` path (about 3.3% slower), so it remains disabled by default. Avoiding allocations alone did not reduce the dominant BNB GEMM time; the next optimization needs to target GEMM or reduce useful physical rows while preserving bitwise outputs.

A second opt-in path calls each BNB 4-bit linear once per sequence row, with rowwise attention, so the quantized GEMM sees M=1 instead of padded M=3. It passed logits/KV probes for M=1…9 on all three tasks (27/27 per measurement type), and matched singleton token/KV state in 6/6 paired pilot rows. It averaged **0.861× vs original BNB** and **1.061× vs fixed-row singleton**. This removes padded GEMM rows but loses the batching benefit; it is also not a speedup over the baseline. See the [summary artifact](llama32_3b_rowwise_linear_summary_v1.json). Neither opt-in experiment is enabled by default.
